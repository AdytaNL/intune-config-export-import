# Intune configuration export and import

**Move Intune device configuration from one tenant to another, including the assignments.**
Three PowerShell scripts export every device configuration policy from a source tenant
as clean JSON templates, let you decide in one mapping file what differs in the target
tenant, and create the policies there through Microsoft Graph.

Background, design choices and pitfalls: [A proven setup: under the hood](https://adyta.nl/en/engineering/a-proven-setup/under-the-hood/).

## Requirements

- PowerShell 7 (the import uses `ConvertFrom-Json -AsHashtable`).
- The `Microsoft.Graph.Authentication` module.
- An account in each tenant that can use the delegated Graph scopes below (an admin consents
  to them once), with an Intune role that allows reading (source) or creating and assigning (target)
  device configuration, for example Intune Administrator.
- Windows for `-Interactive` (it uses `Out-GridView`).
- A test tenant: run the import there first, with `-WhatIf` and then for real, before you
  import into a tenant that is in use.

## Quick start

```powershell
Install-Module Microsoft.Graph.Authentication -Scope CurrentUser

# 1. Export the source tenant
.\Export-IntuneDeviceConfigurations.ps1 -TenantId "<source tenant ID>" -OutputPath "C:\Export\Contoso"

# 2. Generate the mapping file and fill it in (target tenant ID, group names)
.\New-IntuneImportMapping.ps1 -SourcePath "C:\Export\Contoso" -OutputFile "C:\Export\Contoso\mapping-fabrikam.json"

# 3. Dry run against the target tenant, then import
.\Import-IntuneDeviceConfigurations.ps1 -TenantId "<target tenant ID>" -SourcePath "C:\Export\Contoso" -MappingFile "C:\Export\Contoso\mapping-fabrikam.json" -WhatIf
.\Import-IntuneDeviceConfigurations.ps1 -TenantId "<target tenant ID>" -SourcePath "C:\Export\Contoso" -MappingFile "C:\Export\Contoso\mapping-fabrikam.json" -Interactive
```

The full walkthrough, with checks after each step, is in [docs/SETUP.md](docs/SETUP.md).

## Why

A configuration policy is full of references to the tenant it came from. Assignments
hold group object IDs, which differ per tenant. The tenant ID appears as a setting of
its own (OneDrive) or in the middle of a longer value, such as an XML profile in a custom
OMA-URI setting. A copied policy points to another organisation, or to nothing.

On top of that, Intune spreads device configuration over four Graph endpoints, each with
its own way of carrying the settings. The Intune admin center has no option to move a
complete set of policies, with assignments and references, to another tenant.

## What is covered

| Kind | Graph endpoint (beta) | How the import creates it |
|---|---|---|
| Classic profiles | `deviceManagement/deviceConfigurations` | One request |
| Settings Catalog (including LAPS and newer Endpoint Security) | `deviceManagement/configurationPolicies` | One request, settings in the same body |
| Administrative Templates (ADMX) | `deviceManagement/groupPolicyConfigurations` | An empty policy, then each definition value separately, bound to its definition and presentations with `@odata.bind` |
| Legacy Endpoint Security intents | `deviceManagement/intents` | The intent, then all settings in one `updateSettings` call |

After a policy is created, the import assigns it with the `assign` action of its endpoint.

Not covered: compliance policies, apps, app protection, enrollment profiles, scripts and
remediations, Conditional Access, and role scope tags (they are stripped).

## How it works

### Export: two files per policy

| File | Contents |
|---|---|
| `<Type>_<Name>_<Id>.json` | The clean template. The policy's own ID, dates, version and scope tags are removed (nested setting IDs stay). The source tenant ID becomes `{{SOURCE_TENANT_ID}}`, also inside longer strings. Group IDs in assignments become `{{GROUP_<NAME>}}` (exclusions: `{{EXCL_GROUP_<NAME>}}`). |
| `<Type>_<Name>_<Id>.meta.json` | The memory: the original policy ID and name, the source tenant ID, the assigned groups by ID and name (including exclusions), and the original value of every placeholder. |

The export walks every object recursively and checks every string value for the source
tenant ID, so it is also found in a OneDrive setting, an OMA-URI value or an XML blob.

It also writes `_manifest.json`: one overview of every policy with its assignments and
placeholders. That is the documentation of the source tenant at the time of the export.

### Mapping: one file with every decision

`New-IntuneImportMapping.ps1` reads the meta files and writes a mapping file:

```json
{
  "_comment": "Generated by New-IntuneImportMapping.ps1 - fill in the values for the target tenant",
  "_sourceTenant": "00000000-0000-0000-0000-000000000000",
  "SOURCE_TENANT_ID": "",
  "groupMappings": {
    "SG-Intune-Devices-Windows": "SG-Intune-Devices-Windows",
    "SG-Intune-Pilot": "SG-Intune-Pilot"
  }
}
```

- `SOURCE_TENANT_ID`: fill in the tenant ID of the **target** tenant.
- `groupMappings`: source group name on the left, target group name on the right. It is
  pre-filled 1:1. Change only the names that differ.
- `tokenOverrides` (optional): values for your own tokens (see below).

A group name can be the same in every tenant, an object ID never. So the name is the key,
and a naming convention becomes the agreement between tenants.

### Import

Per policy the import replaces the placeholders, reports any `{{TOKEN}}` that is still
open, creates the policy through the route of its kind and then assigns it. Groups are
looked up by display name in the target tenant. A group that is not found is reported.
A missing included group skips only that assignment. A missing **exclusion** group skips
all assignments of that policy, because without the exclusion the policy would reach more
devices than in the source.

Select what to import with `-Filter` and `-Exclude` (wildcards on the file name), or with
`-Interactive`, a selection window that shows the real policy name and the source
assignments. `-WhatIf` shows what would be created without creating anything.

## Things to know before you run it

- **The import does not check for existing policies.** Every run creates new policies.
  Use `-Filter`, `-Exclude` or `-Interactive` when you run it again.
- **Policies are assigned on import.** Groups with the same name in the target tenant
  receive the policy right away. Want to look first? Leave the group names in
  `groupMappings` pointing to a pilot group, or remove the assignments afterwards.
- **Assignment filters are not carried over.** Only the target type and the group are
  exported. A policy that used a filter in the source applies to the whole group in the
  target. Add the filters again after import, before a policy reaches production groups.
- **Group names must be unique in the target tenant.** If two groups share a display
  name, the import does not guess: it reports it and treats the group as not found.
- **A partly created policy is not assigned.** If settings of an Administrative Template
  or an Endpoint Security intent fail, the policy exists but gets no assignments. Fix or
  delete it in the admin center.
- **The mapping belongs to one target tenant.** If `SOURCE_TENANT_ID` in the mapping file
  is not the `-TenantId` of the run, the import stops before connecting.
- **Text values only.** The tenant ID is found in string values. Base64 payloads (for
  example custom OMA-URI XML values and Apple custom profiles) are not decoded; check them.
- **Other tenant-bound IDs.** Settings Catalog policies that refer to reusable settings
  (for example in firewall rules or device control) and Administrative Templates based on
  ADMX files you imported yourself use IDs that only exist in the source tenant. Recreate
  those references in the target.
- **Only the tenant ID and assignment groups are tokenised.** Other tenant-specific
  references are carried over as they are: certificate profiles that point to a trusted
  root or a SCEP/PKCS connector, Wi-Fi or VPN profiles that point to a certificate,
  URLs and domain names of the source organisation. Check those policies after import.
  For a value that differs in the target tenant, put your own token in the clean JSON
  (for example `{{SCEP_URL}}`) and give it a value under `tokenOverrides`.
- **Values that Intune keeps encrypted** (for example some custom OMA-URI values and
  pre-shared keys) are exported the way Graph returns them. Check those profiles after
  import.
- **Treat an export folder as sensitive.** The meta files and the manifest contain the
  source tenant ID and group IDs and names, and the policies may contain internal URLs.
  Do not commit an export to a public repository.
- **Graph beta.** The scripts use the beta endpoint, which Microsoft can change. Test in a
  test tenant first.

## Parameters

### Export-IntuneDeviceConfigurations.ps1

| Parameter | Required | Example |
|---|---|---|
| `TenantId` | yes | `00000000-0000-0000-0000-000000000000` |
| `OutputPath` | yes | `C:\Export\Contoso` |

Delegated scopes: `DeviceManagementConfiguration.Read.All`, `Group.Read.All`.

### New-IntuneImportMapping.ps1

| Parameter | Required | Example / default |
|---|---|---|
| `SourcePath` | yes | `C:\Export\Contoso` |
| `OutputFile` | no | `<SourcePath>\mapping-template.json` |

Runs offline; no Graph connection.

### Import-IntuneDeviceConfigurations.ps1

| Parameter | Required | Example / default |
|---|---|---|
| `TenantId` | yes | `00000000-0000-0000-0000-000000000000` |
| `SourcePath` | yes | `C:\Export\Contoso` |
| `MappingFile` | yes | `C:\Export\Contoso\mapping-fabrikam.json` |
| `Filter` | no | `*.json`; e.g. `"SettingsCatalog_*"` or `"*BitLocker*","*LAPS*"` |
| `Exclude` | no | e.g. `"*Autopatch*"` |
| `Interactive` | no | switch |
| `WhatIf` | no | switch (dry run) |

Delegated scopes: `DeviceManagementConfiguration.ReadWrite.All`, `Group.Read.All`.

File name prefixes the import recognises: `DeviceConfig_`, `SettingsCatalog_`,
`AdminTemplate_`, `EndpointSecIntent_`. Other files are skipped and counted.
